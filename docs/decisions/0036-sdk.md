# ADR 0036: A typed, dependency-free client SDK, with a replayable event stream

## Status
Accepted (2026-10-20). Implements part 3 of Task 12b of `docs/superpowers/plans/2026-10-19-bind-completion-plan.md`
(the typed client SDK). Builds on ADR 0016 (the API is the product surface, and the rebuilt UI, the scripts and the MCP server
use the same contract), ADR 0021 (workspace tokens), ADR 0034 (the registry and the OpenAPI document), and ADR 0035 (the event
stream and its poll fallback). `src/ui/` is not touched (ADR 0016). The wire contract for events is `docs/EVENTS.md`.

## Context
The rebuilt UI, the scripts and the MCP server all call the same HTTP API. Each would otherwise write its own fetch code, its
own error handling and its own event reader, and each would get the same things wrong in a different way: a token in a URL,
a retried POST that places an order twice, a reconnect that skips or repeats events. One small client, written once, with the
rules below enforced in one place, is cheaper than three copies.

The client is not a framework. It has no runtime dependency, because it runs in Node 22 and in browsers and a dependency
would be a supply-chain surface in the browser. It does not import server code, so it cannot drift into trusting the server's
internals.

## Decision

### 1. What the SDK is, and is not
- `sdk/` is a private package, `@bind/sdk`, version `0.1.0` (the API version of `docs/openapi.json`). It has no runtime
  dependencies. Its source imports only its own files, which a unit test checks. It uses `fetch`, `ReadableStream`,
  `TextDecoder`, `AbortController` and `crypto.getRandomValues`, all of which exist in Node 22 and in browsers.
- The caller supplies the base URL and the token. The SDK never reads the environment.
- The SDK has **no authorization of its own**. The server decides what each token may do. The `owner` group names the
  owner-only operations so a caller can see which calls need an owner token; a staff token gets a `BindApiError` with status 403
  from the server.
- The SDK has **no cache**. Every call is a request.
- The SDK **never retries a write**: POST, PUT, PATCH and DELETE are sent once. A retry could repeat an order, a payment or a
  decision.
- The SDK is **not published** (`"private": true`). No npm release, no React hooks, and no pagination helpers, because the API
  has no pagination beyond the event poll's `after` and `limit`.

### 2. The token and the URL
- The token is held in a private field (`#token`). `JSON.stringify(client)`, `String(client)` and `util.inspect(client)` never
  include it. `toJSON` and the inspect symbol are defined for this.
- The token is sent only in the `authorization: Bearer` header of each attempt. It is never in a URL or a query string.
- Every request URL is built from the configured origin and the configured path prefix. A path parameter is percent-encoded. A
  value that is empty, a dot segment, or an absolute URL (`scheme://`, a leading `//` or a backslash) is refused with a
  `TypeError` before any request is made. The final URL is checked to have the configured origin.
- `redirect: "error"` and `credentials: "omit"`. A redirect could carry the header to another origin, and cookies are never used.
- An error message, and an error's `body`, has the token replaced with `[redacted]` if the server ever echoes it. The
  `Authorization` header is never copied into an error.
- A base URL with credentials, a query or a fragment, or a non-http(s) scheme is refused with a `TypeError`. Its text is not
  repeated in the message, because a mistyped URL can carry credentials.
- A token must be a non-empty run of printable ASCII (`bnd_` tokens are). That is stricter than "no whitespace".

### 3. Each request
- Every attempt sends `x-request-id` (`sdk-` and 32 hex digits, which matches the server's rule), `accept: application/json`
  (or `text/event-stream` for the stream) and the bearer token. A `user-agent` is sent only when `userAgent` is set; browsers may
  ignore it.
- The default timeout is 30 s per attempt. The timer covers the wait for the headers and then the body. A timeout aborts the
  request and throws `BindTimeoutError`. A timeout is not retried.
- A caller's `signal` aborts a request, or a wait between attempts, and rejects with the signal's own reason.

### 4. Retries
- Only `GET` and `HEAD` are retried. Up to `maxRetries` (default 2) extra attempts, on a network failure or a 502, 503 or 504.
  The waits are 200 ms and then 400 ms, each multiplied by `0.5 + random()`, so they are jittered. `sleep` and `random` are
  injectable so the tests do not wait.
- A 429 is retried once, after `Retry-After`, when that is 10 s or less. Without a `Retry-After`, the first backoff is used.
  A longer `Retry-After` is not waited for: the 429 is thrown with `retryAfterSeconds`.

### 5. Errors (`sdk/src/errors.ts`)
All extend `BindError`, which extends `Error`. Each has a stable `name`, and `instanceof` works.
- `BindApiError`: any non-2xx answer. Fields: `status`, `message` (the server's `error` string, or `HTTP <status>` when the body
  has no such string), `code`, `reasonCodes`, `requestId` (the response's `x-request-id`), `retryAfterSeconds`, and `body`.
- `BindNetworkError`: no answer. It carries the method only, not the URL.
- `BindTimeoutError`: carries `timeoutMs` only.
- `BindStreamError`: a stream failure that reconnecting cannot fix (see section 6). It carries a `reason`.
- A 2xx body that is not valid JSON is a plain `BindError`.

### 6. Typed operations and the generated files
- `sdk/src/generated/api.d.ts` is generated from `docs/openapi.json` by **openapi-typescript 7.13.0** (a devDependency). It has
  no runtime effect. `npm audit --audit-level=high` reports 0 vulnerabilities with it installed, so the fallback of writing our
  own type generator was not needed.
- `sdk/src/generated/operations.ts` is written by our own code (`scripts/generate-sdk.ts`) from the spec's paths. It maps each
  operation id to its method and path template, and it is typed so that a missing or extra entry is a compile error.
- `npm run sdk:generate` writes both files. Both are committed. The generator is deterministic (two runs are byte-identical).
- Drift is checked by a unit test, `the generated types are current`, which regenerates both files into a temporary directory
  and compares them with the committed ones. The same check, run by hand or in CI, is
  `npm run sdk:generate && git diff --exit-code sdk/src/generated`.
- `client.call(operationId, { params, query, body, signal })` is typed from the generated `operations`. A wrong operation id,
  a wrong parameter name or a wrong body is a compile error. Its result is the parsed 2xx answer, typed; a text route returns
  text, and an answer with no body returns `undefined`.
- Convenience wrappers call `call`. The owner group, `client.owner`, holds the owner-only operations.

### 7. The event stream (`client.events`)
`client.events(workspaceId, { lastEventId?, signal?, reconnectMinMs = 500, reconnectMaxMs = 10000 })` returns an async iterable of
`BindEvent` (the envelope of `docs/EVENTS.md`).
- It connects with `GET .../events`, `accept: text/event-stream` and the bearer header, and resumes with `Last-Event-ID` set to the
  last id it yielded. The query string is not used for the token or the cursor.
- The parser (`sdk/src/events.ts`) follows the WHATWG event-stream rules. Input can be split anywhere. `\n`, `\r\n` and `\r` are all
  line ends. A comment and an unknown field are ignored. Multi-line `data` is joined with a line feed. `id` and `retry` are tracked.
  An event is dispatched only by a blank line, so a trailing partial event is never delivered.
- Each event is yielded once. An event whose id is not greater than the last one yielded is skipped, so a replayed or older event
  is dropped. Ids are compared as `(txid, seq)` numbers, not as text.
- A `shutdown` or `reconnect` event reconnects at once and is not yielded. A server `retry:` value is the minimum delay before a
  reconnect, capped at 60 s.
- Reconnect delay: for attempt `n`, `cap = min(reconnectMaxMs, reconnectMinMs * 2^(n-1))` and the delay is drawn from
  `[cap/2, cap]`. The attempt count resets when a chunk arrives.
- It reconnects after a clean close, a network failure, a timeout, a 429 (honouring `Retry-After`, up to 60 s) and a 5xx.
- It **stops with the error** on a 401, a 403, a 404 and any other 4xx. These are not retried. A revoked token ends a stream this
  way: the server ends the stream when its token is revoked, the reconnect is refused with 401, and the caller gets a
  `BindApiError`. A 2xx answer that is not `text/event-stream`, a frame whose data is not the envelope, or an event with a bad id,
  is a fatal `BindStreamError`.
- Breaking out of the loop, or aborting the signal, cancels the body reader and aborts the request. The generator ends quietly
  (no throw), and no timer or listener outlives it.

**Pinning (no gap when the caller gives no start point).** When `events()` is called without `lastEventId`, the client reads the
workspace's current cursor once, from the poll endpoint (`pollEvents` with `limit: 1`, whose `nextCursor` is the newest event's id,
or `0.0` for an empty history). That cursor is the stream's first `Last-Event-ID`, and every later connect and reconnect sends
`Last-Event-ID`. So events written after the `events()` call are delivered, including those written before the first connection
succeeds, and those written while a connection is down before any event was received.
- The pin is requested at the `events()` call, not at the first read. This is what "pinned at call time" means: the cursor is taken
  before the caller can write, so a caller that writes and then reads does not lose those writes.
- The pin request goes through `call()`, so it has the GET retry rules (network failures and 502, 503, 504, with backoff). A pin that
  still fails with a network error, a timeout, a 429 or a 5xx is retried by the stream with the same backoff as a reconnect. A pin
  that fails with 401, 403, 404 or another 4xx ends the stream with that `BindApiError`, and no connection is opened.
- A caller that passes `lastEventId` is not pinned: no poll request is made, and the caller's cursor is used as given.
- Fallback: if the poll answer has no `nextCursor`, or one that is not in the `<txid>.<seq>` form, the stream does not pin and
  starts at the server's default rule (after the newest event at connect time, ADR 0035). This is the only case in which events
  written in a gap can be missed, and the SDK does not hide it.

### 8. Browsers
- A browser cannot use the native `EventSource` for this API, because `EventSource` cannot send an `Authorization` header. Use
  `client.events()`, which uses `fetch`.
- Token handling is the caller's job. The SDK does not store the token.
- Never ship an owner token to a browser you do not control. An owner token can change policy and approve payments. Prefer a
  narrower token, and revoke it when the page is retired.

## Tests
- `tests/unit/sdk.test.ts`, mock fetch: the titles of the brief, plus three checks of the packaging boundary (the source imports
  only its own files; the package is private, has no dependencies and carries the API version; a call to an unknown operation is a
  compile error).
- `tests/unit/sdk-sse.test.ts`: the parser (the brief's six titles).
- `tests/unit/sdk-stream.test.ts`: eight extra tests of the reconnect and pinning rules with a scripted fetch: a replayed event is
  yielded once and never goes backwards; a 401 on reconnect ends the stream with no further request; the server retry is the
  minimum delay; a shutdown event reconnects at once and is not yielded; breaking out cancels the body and aborts the request; a
  non-stream 2xx answer is a fatal `BindStreamError`; a caller supplied `lastEventId` is not overridden by pinning; a pin that
  answers 401 is fatal, and a pin that fails with a network error is retried.
- `tests/integration/sdk.test.ts`: the real server on port 0, PostgreSQL, real tokens and real streams (the brief's titles, plus two
  pinning tests, 14 in all). A cut connection is a `destroy()` of every server-side socket. The reconnect tests take about 3 s
  each, because the server sends `retry: 3000`. The pin test holds the stream connection with a gate in the test's fetch wrapper;
  the pin request itself is not held. It is the client, not the server, that is delayed, so the stream connection is
  delayed as the test needs.
- Mutation check of the pin: removing it fails both pinning integration tests (events written before the first connection, and
  events written during an outage before any event was received), and the pinning unit test with the network error (it expects a
  pin request and a start from its cursor). The pinning tests were written after the pin was implemented, so they were not seen
  failing first; the mutation check is the evidence that they test the pin.

## Deviations from the brief, and why
- `cancelWorkflow` is in the `owner` group, not among the top-level wrappers. The registry gives it `access: "owner"`, and the
  brief asks that owner-only operations be clearly separated so that callers see the difference.
- `setAgentsPaused(id, paused)` takes a boolean, not a body. The body has only that field.
- `reconcileOrder(orderId)` and `confirmOrderSettlement(orderId)` take the order's own id. Their routes are not under a workspace.
- The token rule is printable ASCII, not merely "no whitespace".
- A base URL with a query or a fragment is refused as well as credentials.

## Consequences
- Three clients (the UI, the scripts, the MCP server) share one set of rules for tokens, retries and reconnects.
- Adding an operation to the registry requires `npm run sdk:generate`. The staleness test fails until it is run and committed.
- The SDK's behaviour on a fatal error is a stop, not a silent retry. A caller that wants to keep a stream alive after a 401 must
  start a new one with a new token.

## Not done
- Not published to npm. No React hooks. No pagination helpers (the API has none).
- No browser run. The SDK is exercised in Node 22 only, through `fetch`, `ReadableStream` and `TextDecoder`, which are the same
  APIs a browser provides.
- The CI workflow (`.github/workflows/quality-gates.yml`) is not edited by this change. The staleness check is a unit test, which
  runs with `npm run test:unit`.
