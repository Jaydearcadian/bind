# 0073: A Privy embedded wallet for each person who signs in with Google

Status: Accepted. Builds on ADR 0072 (sign-in), 0071 (the Privy browser adapter and its wallet methods) and 0070 (the CSP). Payments through Arc are ADR 0060; none of that is built.

## Decision
- **Who gets a wallet, and when.** A person who signs in with Google gets a Privy embedded wallet created automatically on their first Google sign-in, one wallet per person. The owner chose "automatically" and "each person's own" (not one per workspace). Someone who signs in with their own wallet keeps that wallet and gets no second one, and quiet re-entry never creates one. If a wallet already exists it is reused; a second sign-in never makes another.
- **What it is for.** Today, nothing: it gives a person an address they can receive to, ready for payments through Arc later (ADR 0060). Creating it moves no money. The business's payment account is a separate decision, so no one person's login holds the company's money by default.
- **What Bind never does.** Bind's server never sees, stores or uses a wallet key. The browser adapter exposes no way to sign or send (checked by tests, down to the module's exports). Agents cannot spend from it. When a business pays, an owner still approves it (ADR 0021 and the commitment gate).
- **Never in the way of signing in.** If wallet setup fails, sign-in carries on; a flag in the tab makes Settings say "Setting up your wallet didn't finish" and offer "Set up my wallet" again.
- **Where it shows.** Settings, "Your wallet": the public address with Copy, and the plain statement of what it is. With an access key there is no wallet and the section says why. With an account session but no Privy session in the tab, it says to sign in again to see it. Bind does not store the address on its server; the page reads it from Privy while signed in.
- **Privy's setting for this app.** The app reports `embedded_wallet_config.mode = "user-controlled-server-wallets-only"`, no password required, create-on-login off. In that mode the SDK creates the wallet through Privy's own service (`POST /v1/wallets`, authenticated with the person's access token) instead of the browser frame, so nothing about the Privy app secret is involved and no Bind server code is. All calls go to `https://auth.privy.io` (no custom API host is configured), which `connect-src` allows; the wallet frame is also allowed by `frame-src https://auth.privy.io` (ADR 0070) but is not used in this mode.
- **Recovery** is Privy-managed. Bind adds no passcode. A passcode-based recovery, where only the person's own secret can restore the wallet, would be a product choice for later.

## Evidence
`tests/web/wallet.spec.ts` (desktop and phone) with the stand-in Privy adapter: a first Google return creates the wallet exactly once, sign-in carries on, and Settings shows the address; a later visit shows the same address and creates nothing; a failed setup does not block sign-in, Settings offers a retry, and the retry shows the address; a wallet sign-in and a quiet re-entry never create a wallet; with an access key Settings explains there is none. `tests/unit/web-privy-adapter.test.ts` (88 tests): single creation under concurrency, an external wallet is never taken for the embedded one, a failed create re-reads before reporting failure, the frame is created lazily, once, only on the exact `auth.privy.io` host, only messages from that frame's own origin and window are accepted, the poster never uses `*`, no signing method exists, and the server-wallets mode result is read from the refreshed user. `tests/integration/csp-policy.test.ts` pins the policy. `LOCAL_PASS`.

## NOT_RUN
Creating a real wallet with Privy. Everything above runs against a stand-in or fakes. What could still fail live, none of it checked: Privy's server-wallet response listing the new wallet in a shape the adapter doesn't recognise (it then reports "wallet not found" instead of creating a second one); a lag before the new wallet shows up; the frame's sandbox flags; and the real custody and recovery behaviour of this Privy mode. A person must sign in with Google on the deployed site and check Settings.

## Not done
Using the wallet for anything (receiving payments, Arc, the ramps); a business wallet; showing balances; exporting or recovering a wallet; creating a wallet for someone who signs in with a wallet, if wanted later.
