# 0072: Signing in with Google or a wallet

Status: Accepted. Builds on the account layer (ADR 0052), Privy as the identity provider (ADR 0051), the CSP (ADR 0070) and the self-hosted Privy bundle (ADR 0071). The people and invite screens are ADR 0064.

## Decision
- **The sign-in page** offers "Continue with Google" and "Continue with a wallet", with the access key form kept underneath ("Or use an access key") for builders and early testers. The buttons only appear when the server has a Privy app (`GET /api/public-config` returns an app id). Without one, the page says account sign-in isn't switched on and the access key still works; nothing pretends.
- **Privy proves who someone is; Bind decides everything else.** After Privy, the page takes a fresh Privy access token and asks Bind for a session: `POST /api/auth/session` swaps it for a short-lived session in one workspace the account belongs to. A wallet sign-in is identity only and never grants payment authority.
- **After identity, one of four screens:** an invite waiting in this tab (a plain "you'll join as staff" with an optional name, then `acceptInvite`); no workspace yet ("Start a workspace": a name for you, a name for it, the kitchen team, which is the only ready team); exactly one workspace (straight in); several (a chooser with the last one opened first).
- **What the browser keeps.** The Bind session (`bns_`, ADR 0052) is kept for this tab only (sessionStorage), never the device. The Privy SDK's own tokens are kept in sessionStorage too (ADR 0071), so closing the tab signs out. Only the last workspace id (not a secret) is remembered on the device, to pre-select it. This is a deliberate step back from the brief's "session lives in memory": the app is several pages, and memory would not survive a page change.
- **Quiet re-entry.** An app page that gets a 401 (the session ended) sends the person to sign-in, which, if the Privy session in the tab is still good and the last workspace is known, mints a new session and returns without asking. It is allowed once per ten seconds so a page that keeps refusing a fresh session cannot loop.
- **Sign-out** is one function (`signOutNow` in core.js) used by every page: it ends an account session on the server, forgets the key, and flags the sign-in page to end the Privy session in the tab (the page holds the bundled SDK). Expiry uses the quiet path; only a deliberate sign-out ends Privy.
- **Google return.** Privy sends the person back to `/app/sign-in?privy_oauth_code=...`. The adapter takes the one-time codes out of the address bar before using them, even if the login then fails.
- **Invite links** (`/app/join#bni_...`) lead into sign-in when it is switched on; the code waits in this tab's sessionStorage and is used by the invite screen. Without sign-in the page says so and keeps the link.
- **The test seam.** The page accepts an adapter in `window.bindPrivyAdapter`, with the same shape as the real one. The browser tests use it, because the real SDK needs the live Privy service. It cannot create a login: whatever token the adapter hands over is verified by the server against Privy's published keys, so a stand-in can only hold tokens the server accepts.
- **Server settings (set by whoever runs Bind, not by owners):** `PRIVY_APP_ID` and `PRIVY_VERIFICATION_KEY` (one or two P-256 public keys, ADR 0052 rotation). The app secret is not used and is not stored.

## Evidence
`tests/web/account-signin.spec.ts` (desktop and phone), against the real server with a throwaway test key whose public half the test server trusts (`tests/web/support/privy-test-key.ts`): a first sign-in starts a workspace and signs in as its owner with a real `bns_` session and nothing in localStorage; a second sign-in goes straight in, and with two workspaces it asks and puts the last one first; an invite link carries through sign-in, the person joins as staff with their name, the invite is used up, and reusing it fails in plain words; an ended session signs back in quietly without looping, and signing out ends the session, forgets the key, ends the Privy session and does not re-enter; coming back from Google strips the codes from the address bar; an expired, other-app or tampered token is refused in plain words and never gets a session; where sign-in isn't switched on the page says so and the invite page says the same. `LOCAL_PASS`.

## NOT_RUN
Live Google and wallet login against Privy itself. The tests prove everything after the adapter; the SDK's real network calls, the Google consent screen and a real wallet signature need a person on the deployed site. Also not covered: Privy features beyond Google and wallet (email, passkey), linking Google and a wallet to one account, and a workspace switcher in the header for people in several workspaces (the chooser appears at sign-in only).
