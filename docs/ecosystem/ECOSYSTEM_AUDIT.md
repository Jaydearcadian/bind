# Bind ecosystem audit, round 1

Status: written 2026-10-20. This round ran four of the command modes against the interfaces that already exist: Ecosystem Handoff Audit, Capability Map, Exposure Audit and Interface Slop Audit. It designs nothing new. It decides what each existing interface is, what it must not be, and what has to be specified before more is built. The 67 API operations, the SDK, the 17 MCP tools and the event stream were read in this repository; nothing was run against a live service.

Evidence for every claim is a file in this repository. Where a claim rests on a test, the test is named.

## 1. Ecosystem handoff audit

**Product truth in force** (`BIND_BUILD_SPEC.md`, `AGENTS.md`): Bind is a deployment and connectivity layer. A business connects once, sets preferences and authority, and gets role-specific agents. The first vertical is a kitchen. Authorization, tenancy, approval thresholds, budgets, idempotency and state transitions are enforced in code outside the model. A quote request is not an accepted offer; a submitted transaction is not confirmed settlement. Tool output and supplier text are untrusted. No live money, mainnet, or real commercial commitment without explicit authorization.

**Consumers that exist today**
| Consumer | Surface | Evidence |
| --- | --- | --- |
| The owner and staff, through the UI that will be rebuilt | the HTTP API, the SDK | `docs/openapi.json`, `sdk/`, ADR 0016 |
| A business's own agents | the MCP server (staff token, 17 tools) | `mcp/`, ADR 0037 |
| A business's messaging surfaces | one inbound signed webhook | ADR 0022 |
| Operators | `/health`, `/ready`, `/metrics`, scripts | ADR 0032 |

**Consumers that do not exist yet:** third-party developers, partners, other people's agents, and any payer of a machine resource. No document names a first external developer audience. That is the largest unresolved input to this work (section 7).

**Domain objects:** workspace, token, role, approval, order, workflow, customer order, menu item and proposal, inventory item, supplier, surface binding, connector, document, ledger entry, audit event.

**Authority boundaries in code:** two roles (owner, staff) per workspace; 404 across workspaces; owner-only decisions; a pause switch; a commitment gate that every commercial commitment passes; agent roles whose forbidden capabilities are rejected server side.

**Protected decisions (not reopened here):** ADR 0005 (approvals decide once), 0017 (effects ledger), 0021 (tokens), 0022 (webhook identity), 0023 (pause covers payments), 0034 (the contract), 0035 (events), 0037 (MCP is member-only).

## 2. Capability map

`docs/capabilities.json` is the machine-readable catalogue. It is generated by `npm run capabilities:generate` from the API contract, the reviewed classification in `docs/ecosystem/exposure.json`, and the real SDK and MCP surfaces, and `tests/unit/capabilities-catalogue.test.ts` fails when it is stale or a rule below breaks.

| Count | |
| --- | --- |
| Operations | 67 |
| Reads | 30 |
| Owner decisions (approve, reject, publish, cancel, confirm) | 10 |
| Owner configuration (policy, pause, roles, suppliers, surfaces, capacity) | 8 |
| Credentials (tokens, connectors, webhook secret) | 7 |
| Commercial commitments | 4 |
| External requests | 3 |
| Data entry | 2 |
| Operational (reconcile, recover, confirm settlement) | 3 |

**Effect classes.** `read`, `external_request` and `commercial_commitment` are the three in `BIND_BUILD_SPEC.md`. Five more were needed to describe the API honestly: `data_entry` (plain operational data), `owner_decision` (an owner's authority act), `owner_configuration`, `credential`, and `operational` (reconciliation and recovery). They are an addition to the spec's vocabulary, not a change to its rules.

## 3. Exposure audit

Every operation has one primary exposure class in `docs/ecosystem/exposure.json`:

| Class | Count | Meaning |
| --- | --- | --- |
| `public_api` | 57 | A business capability for the owner's UI and, later, external developers |
| `internal_service` | 6 | Platform or operator use; not for external builders, the SDK convenience layer, or agents |
| `protocol_primitive` | 4 | The contract, the signed inbound webhook, the event stream and poll |

No operation is `private_partner`, `agent_facing`-only, or a `paid_machine_resource`: none exists. Agent reach is a property of the MCP projection (17 tools), not a class.

**Decisions**
- **E-1. Keep internal.** `reconcileOrder`, `confirmOrderSettlement` and `recoverWorkflows` are reconciliation internals. They stay in the API for the owner's console but are marked `internal`: not in the public reference, not an SDK convenience method, never an MCP tool. `getHealth`, `getReady` and `getMetrics` are platform probes, also `internal`.
- **E-2. Never expose to agents.** Every `owner_decision`, `owner_configuration`, `credential` and `operational` operation. The catalogue test enforces this against the real MCP tool list.
- **E-3. Only three agent tools can start a commercial commitment**: `request_replenishment`, `create_customer_order`, `cancel_customer_order`, and only through the commitment gate. The test fixes the list, so adding a fourth is a deliberate edit.
- **E-4. Preview, not stable.** Documents, ledger, templates, `createWorkspace`, `onboardWorkspace` and `verifyConnector` are `preview`. Their semantics are still moving (no live verifier, templates half data and half code).

**Rejected exposures**
- A generic "update any record" route, a raw database or ledger writer, a workflow-step API, and an administrative "run recovery as a customer" route. None exists, and none should.
- Machine-paid access (x402, MPP) to anything today. See section 5.

## 4. Interface slop audit

Findings from reading the contract, the SDK, the MCP tools and the event docs. "Evidence" is where to check.

| # | Finding | Evidence | Severity |
| --- | --- | --- | --- |
| S1 | **No client idempotency key.** Repeats are safe only by natural keys (`externalRef` on customer orders, feedback duplicate detection, a repeat replenishment while the workflow awaits approval returned the same workflow in the model check, ADR 0042). Every other command has no documented retry behaviour. The SDK correctly retries only GETs. | `docs/openapi.json` has no `Idempotency-Key`; `tests/unit/capabilities-catalogue.test.ts` pins this | High |
| S2 | **Error contract is thin.** `{ error, code?, reasonCodes? }`. No category, retryability, recovery actions or request id in the body (the id is a header). | ADR 0034 section 4, `ErrorBody` | Medium |
| S3 | **Several responses are database-shaped.** Rows read with `SELECT *` are returned as stored (snake_case) for inventory, suppliers, approvals, orders, workflows, ledger, audit; service views are camelCase. | ADR 0034 section 3, ADR 0041 | Medium |
| S4 | **Events are audit rows.** The event type is the audit action string, several in the present tense (`commitment.evaluate`, `orders.submit`). The envelope has no schema version, object version, or correlation id, and nothing is signed. | `docs/EVENTS.md`, `EventEnvelopeSchema` | Medium |
| S5 | **Polling plus one stream is the only way to follow changes.** There are inbound webhooks but no outbound, signed, replayable webhooks for developers. | `docs/EVENTS.md`; no outbound sender in `src/` | Medium |
| S6 | **Authorization is two roles.** There are no domain-action scopes. An agent holds a staff token, so the MCP allowlist is enforced by the MCP server, while the token itself can call every member route (for example `fulfilCustomerOrder`, `upsertInventoryItem`, `extractDocument`) if used directly. The model never sees the token, so this is not exploitable through MCP, but the restriction is not enforceable at the API. | `docs/ecosystem/exposure.json`, ADR 0037 | Medium |
| S7 | **A secret is readable repeatedly.** `getWebhookSecret` returns the surface secret on every call; tokens and `rotateWebhookSecret` show theirs once. | ADR 0022 | Medium |
| S8 | **Two creation routes.** `createWorkspace` overlaps `onboardWorkspace`. | `docs/openapi.json` | Low |
| S9 | **Generic upserts** for inventory, suppliers, agent roles and surface bindings. They are plain data or owner-only, so they are not lifecycle bypasses, but they carry no expected version (last write wins). | `exposure.json` flag `generic_upsert` | Low |
| S10 | **MCP has tools only.** No resources for readable state and no prompts for user-invoked workflows. Tool results are structured and mark untrusted text fields. | `mcp/README.md` | Low |
| S11 | **No versioning or deprecation policy.** The contract is `0.1.0`, routes are unversioned, and there is no stability, support window or migration guide. Stability now exists per operation in `exposure.json`, but is not published to consumers. | `docs/openapi.json` | Medium |
| S12 | **No developer journey or external conformance suite.** The contract tests are internal. There is no quickstart, sandbox profile or runnable example for an outsider. The simulators are labelled, but there is no "sandbox token" concept. | repository docs | Medium |
| S13 | **Response semantics lack next actions and freshness.** Responses do not list available next actions or links. | `docs/openapi.json` | Low |
| S14 | `createCustomerOrder` answers 201 for declined or held orders. A known quirk, already recorded. | known issues | Low |

**What already passes**
- The SDK is a generated transport plus a handcrafted layer; it does not retry unsafe commands and does not hide asynchronous state.
- MCP tools return structured results and mark untrusted fields; an operation allowlist is checked against the contract at start-up.
- Async work is a resource, not a status flag: replenishment returns a workflow, and a held order says so.
- The event stream has a safe cursor, replay, per-role filtering and an allowlisted payload.
- Errors reach clients in a fixed, safe form with no raw exceptions (ADR 0031; tests in `tests/integration/error-echo.test.ts`).

**The nine tests, applied to the interfaces as they are**
| Test | Result |
| --- | --- |
| Capability | Pass for the 57 business operations; the 6 internal ones are correctly not public |
| Projection | Pass for MCP (a deliberate subset); partial for the SDK (a generic `call` reaches every operation) |
| Misuse | Partial: S6 and S7 |
| Agent | Partial: no resources or prompts (S10); tool descriptions had one wrong claim, fixed in ADR 0042 |
| Payment | Not applicable: no paid resource exists |
| Failure | Partial: S2 and S1 |
| Privacy | Pass: events allowlist, redaction, tenancy (ADR 0031, 0035) |
| Evolution | Fail: S11 |
| Ecosystem | Fail: S5 and S12 |

## 5. Payment surface

**Decision P-1: build none now.** No capability has a price, an external payer or a distribution reason, and `AGENTS.md` forbids live money. Settlement inside the product (Arc, simulated by default) is a business operation, not machine-paid access, and it must not be reused as one. When a paid resource exists, payment goes behind an adapter, stays separate from authority (a payment never grants permission to do a prohibited action), and starts on a test network only. Candidates worth evaluating later, none of which is a commitment: a market-benchmark lookup, a document extraction call, a read-only capability catalogue for partners.

## 6. Decisions recorded

| ID | Decision | Reason | Reconsider when |
| --- | --- | --- | --- |
| D-1 | The first external consumers are the owner's own UI (through the SDK) and the owner's own agents (through MCP), not third-party developers | No document names another audience, and the product is pre-UI and pre-live | The owner names a partner or developer audience |
| D-2 | `docs/capabilities.json` is the catalogue; `exposure.json` is the reviewed classification; both are tested | One source for docs, SDK reference and MCP registration to be projected from | A capability is added or reclassified |
| D-3 | Internal operations stay in the API but are excluded from public surfaces | The console needs them; external builders must not | A recovery capability becomes safe to automate |
| D-4 | No payment protocol is built | See P-1 | A paid resource and a payer exist |
| D-5 | Specify before building: the next change is a written Response Model and Event Surface, then additive code | The prompt's own rule, and S1 to S5 are all additive | The owner prefers to ship first |

## 7. Unresolved assumptions

1. Who the first external developer audience is, if any. (D-1 assumes none.)
2. Whether the owner wants a public API reference and an external conformance suite soon, or only a private one for the rebuilt UI.
3. Whether staff tokens should gain domain-action scopes (S6). That changes the trust model and needs its own decision, not a patch.
4. Whether `getWebhookSecret` may keep returning the secret (S7).
5. Whether the casing mix (S3) is to be fixed with an SDK mapping layer (ADR 0041) or a versioned API.

## 8. Next evidence-producing step

Run **Response Model** and **Event Surface** as a written specification, with no code. It would define, additively: an `Idempotency-Key` for the four commercial commands; an error body v2 (stable code, category, retryable, recovery actions, request id); and an event envelope v1 (schema version, object version, correlation id, past-tense names kept alongside the current ones, and a signature for any outbound webhook). The evidence is a reviewed contract change that the existing contract tests can check, which is cheaper to get wrong on paper than in the server. Everything in sections 4 to 6 is a candidate for that step; nothing here has been built.
